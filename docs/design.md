# Design notes: the SQL, the runner, the rules, the models, and the cost model

The long form behind the README. Read `docs/runbook.md` first if you are here to run the tutorial; read this when you
want to know why a file does what it does. The evidence for every rule is in `docs/sanity_findings.md` (the item ids,
vocabularies and ranges, tested before use) and `docs/cohort_findings.md` (the six ICU cohort runs and what each
check table changed); the model runs are in `docs/model_findings.md`, with the evidence run's output in
`docs/model_results/`.

## SQL (BigQuery Standard SQL, physionet-data.mimiciv_3_1_hosp / _icu)

The SQL is BigQuery Standard SQL and runs on BigQuery against `physionet-data` through `pipeline/run_bigquery.py`, which fills the `YOUR_PROJECT` placeholder from its `--project` argument (or by hand in the console). The files run in order; each prints aggregate check tables (never row-level data), which the runners save as CSV. `00` and `00b` are the only files that read the source tables; `00b` runs once, and `01` and `02` read its extracts, so they can be re-run while their DECLAREs are tuned (see Cost below).

## The runner: pipeline/run_bigquery.py

`--step extract` first writes and drops a one-row table, so a project whose lifetime sandbox storage is spent fails in seconds with an explanation instead of after a 16 GiB scan (the quota is per project: a new project has its own 10 GiB; a project with billing has no cap and pays about $0.02 per GB-month). It then runs `00b_extract.sql` as one BigQuery script job in your project and reads the script's child jobs: one line per statement with its type and bytes billed (the cost table below is filled from here, not from estimates), and the `__TABLES__` size table as CSV. It refuses to run when `src_*` already exist, because a second run spends another 2.78 GiB of the lifetime 10 GiB (the extract's own size table); `--force` overrides.

`--step pipeline` runs `01` and `02` the same way and writes every check table to `results/checks/` as CSV, so nothing is copied out of the console by hand (`01_cohort_labels_table01.csv` to `table21.csv`, named after the `-- Table N.` headers so that a view added to the file does not rename them; `02_features_check01.csv` the leakage assertion, `check02` Table 1b, `check03` the profile, by statement index; before release .22 every file was numbered by statement index, `check15` being table 1 of `01`). Repeatable at the cost of query bytes only; `--only 02_features.sql` re-runs one file after a change to it, provided the objects it reads already exist in the project.

`--step pull` issues one ordered `SELECT *` per final object (`params`, `cohort_landmarks`, `features`; the rows ordered by subject, stay and landmark so two pulls give the same file) and writes each as parquet. The result rows travel through the BigQuery Storage Read API when the project allows it (reads of query results are free and do not count against that API's own 300 TiB monthly tier, per the pricing page) and through the plain REST read otherwise; the client library falls back on its own.

`--step cost` prints the month's billed query bytes against the free 1 TiB and the dataset's storage against the sandbox's lifetime 10 GiB, so a student can see where they stand before running anything.

Authentication is whatever Google's client library finds: in Colab, `auth.authenticate_user()`; on a laptop, `gcloud auth application-default login`. The runner was exercised end to end against a simulated BigQuery client before the first real run; the cost table below holds the measured numbers of the real runs.

## Rules the SQL encodes

The hypotheses behind these rules, the numbers that tested them, and the verdicts are in `docs/sanity_findings.md` (the item ids, vocabularies and ranges) and `docs/cohort_findings.md` (the first run of 01 and 02 on the ICU cohort: the thirteen tables, the 948-row leakage finding and its fix, the two open questions Tables 12 and 13 answer). The deck's lesson slides and their speaker notes are built from those files.

- Landmarks t_k = ICU intime + 24·k h, k = 1..28 (`MAX_K`; 00 section M: k ≤ 14 would lose 12% of rows, from the 3.6% of stays longer than 15 days); a row exists while the patient is in the ICU and alive; it is at risk only if insulin (or a sulfonylurea or meglitinide) was given in [t_k − 24 h, t_k): a subcutaneous or bolus dose in the window, or a drip segment overlapping it.
- Labels use glucose charttime in [t_k, window_end), window_end = the earliest of t_k + 24 h, ICU discharge and death, from `hosp.labevents` (50931, 50809, 52569) and `icu.chartevents` (220621, 225664, 226537), de-duplicated. The primary label `y_lt54_24h` counts every documented result below 54 in the window (release .22). The repeat-result rule, CMS816's exclusion for its < 40 measure (a result followed by a glucose above 80 within 5 minutes), flags a result below 54 contradicted by any result above 80 charted within 300 seconds (results at or above 54 are never flagged; until release .20 the flag had no "low" condition and cancelled normal and high values too, which the first review found). The flag establishes that the low was contradicted, not why (treatment between two draws, two sampling methods and meter error all produce the pattern), so it is used only where CMS defines it: in the CMS816 secondary outcome (`y_cms816_24h`: a result below 40 not excluded by the rule, with a hypoglycemic agent in the 24 h before it) and in the sensitivity endpoint `y_lt54_excl_24h`, which the notebook's fifth sensitivity refits arm B on; releases .20 and .21 had used it in the primary label. `y_lt40_24h` counts every documented result below 40. Events after ICU discharge are not observed, so the window is truncated there; `window_hours` is on every row and the notebook drops rows under 6 h as a sensitivity.
- Only values in [GLUCOSE_MIN, GLUCOSE_MAX] = [10, 2000] mg/dL enter the stream (00 H2, H6: charted ICU values include −124, 0, 0.12 and 1,653,550; the fingerstick item piles up at exactly 0, the meter "LO" reading; 01 table 9 counts the zeros that fall in a label window as the stated sensitivity).
- Drips come from `inputevents` (00 K2): a "Continuous Med" row with a rate in units per hour is a segment; a rate-less "Continuous IV" row (2,245 in MIMIC-IV) is a segment with rate = amount / hours; a "Bolus"-status row on the drip is a bolus of its amount, never a segment; rows with `statusdescription = 'Rewritten'` are superseded and dropped; rates above `DRIP_RATE_MAX` = 100 units/h and amounts above `DOSE_MAX_INSULIN_UNITS` = 200 are flagged, never used. Drips also come from the eMAR (`emar_insulin_infusions`): the first ICU run's table 12 found eMAR infusion starts on 20% of eligible stays in every era from 2017 on while inputevents drip rows fell from 20% to 9% of stays in 2020 to 2022, so a rule reading inputevents alone lost more than half of the test era's drips. An eMAR interval opens at a Started / Restarted event, or at a Confirmed when none is open, and closes at the earliest of the first Stopped, the next start, and `INFUSION_CAP_HOURS` = 16 after its last start or confirmation (since release .22 the cap binds even when a Stopped exists: a Stopped charted more than 16 h after the last evidence is a drip that ended earlier and whose end was charted late, so it cannot stretch the interval across the silence). The cap was 48 h (00 F) until the third ICU run measured, inside intervals a Stopped did close, the longest gap between consecutive events: 6.5 to 7.4 h at the median, 9.3 to 9.5 at the 90th percentile and 12.8 to 16.3 at the 99th in every era (01 table 15), so a drip still running leaves a new event within 16 h in 99 of 100 cases; at 48 h the "running" rows included ones checked a third less often than the rest (table 7). Table 7 splits the running rows by the record that says so and shows the rows the flowsheet-first rule declines. `drips_at_landmark` holds both as each landmark could see them (see Availability below); the rule that reads it is flowsheet first: the eMAR state counts only while the stay's flowsheet has shown no insulin drip segment by t_k (`stay_has_inputevents_drip`, evaluated per landmark from segments both started and entered before t_k). The fourth ICU run's table 7 decided that: where the flowsheet is complete, a row "running" on an eMAR interval alone was checked 8 to 10 times in 24 h with the no-drip event rate (0.9 to 1.3%), an interval that outlived the drip (the Stopped charted late, or the cap), while in 2020 to 2022, where the flowsheet is absent, the same rows were checked 12.7 times with the drip rows' event rate (2.4%). The at-risk rule, `drip_running_at_tk` and 02's drip hours apply it; rates come from inputevents only; the bookkeeping flags `drip_inputevents_24h`, `drip_emar_24h`, `drip_running_inputevents_at_tk`, `drip_running_emar_at_tk`, `stay_has_inputevents_drip` and `emar_interval_open_at_tk` say which record saw the drip and what the rule declined.
- Subcutaneous doses are counted once: eMAR first; an `inputevents` bolus is added only when no eMAR insulin bolus sits within `SOURCE_MATCH_MINUTES` = 60 on the same admission. 00 L found the two sources overlap only partly (46% of eMAR ICU boluses have an inputevents row within 60 min, 38% the other way round), so the union is the rule; 00 L2 showed the match rate climbs only to 48% at 120 min and 51% at 240 (62% at 12 h, what frequent dosing produces by chance), so a clock offset is ruled out and the sources chart different doses; 01 table 5 shows the share per source.
- eMAR data model (00 C, D, G, I, and the first 01 run): doses sit on child rows and are summed per emar_id; "Not Given per Sliding Scale" is a check with nothing due (`n_ss_no_dose_24h`), not a held dose (`n_insulin_held_24h`); NULL event text with a charted dose is an administration; "Confirmed" is the nurse's check of a running insulin infusion, drip evidence and never a dose (01 table 13 on the first ICU run: 48,861 of 48,864 cohort rows carry the administration type "Insulin Infusion (IV Drip)", 72.8% sit inside an inputevents drip segment, 0.4% carry a dose; 00 D2 had read them as pump patients, and the 19 real pump rows are kept apart by their medication text); it feeds `emar_insulin_infusions` and is excluded from `bolus_given` and `sc_doses`; route is never populated for insulin, so IV push protocols are recognised by name; `dose_given` holds barcode-sized values and is capped (`dose_given_raw` keeps the raw sum).
- Feeds and dextrose from `inputevents` (00 K, N): the item category decides enteral and parenteral before any label regex ("Boost Glucose Control" is a feed, "Dextrose PN" a TPN component), dextrose 50% is its own item, and the remaining dextrose fluids are mostly two-hour carrier bags, so that feature is a rate in mL/h. Running and hours features use rate rows only (`has_rate`, rates above `FEED_RATE_MAX` = 500 mL/h flagged); amount rows are boluses and flushes. Features: enteral running at t_k, hours in the last 24 h, rate, interruption (fed in the last 24 h but nothing running at t_k; 00 N2: one consecutive segment pair in eight has a gap of over an hour, so interruptions are measured, not inferred) and hours since it stopped; parenteral; dextrose fluid rate and hours; dextrose 50% counts (and, in 01 table 8, the share of < 54 events followed by D50 within 2 h, the evidence that the label finds treated events).
- ICU vitals keep the mimic-code vitals_first_day plausibility bounds; weight (226512, 224639) is kept in 20 to 400 kg with omr as the fallback; the three GCS components are summed per charting time and the 24 h minimum is a feature; ventilation at t_k from `procedureevents` 225792 / 225794; vasopressors from the seven mimic-code items.
- Dialysis, infection and octreotide (00 O, O2, P, P2), the ICU hypoglycemia risk factors the first feature set lacked (Vriesendorp 2006: CVVH with bicarbonate replacement fluid OR 14, sepsis OR 2.2, octreotide OR 6.0 with a wide interval; Krinsley 2007 and Waeschle 2008: sepsis severity). Dialysis comes from two sources merged per stay (00 O2: CRRT charting covers 2,927 stays against 2,274 with a procedureevents interval, all but 3 of them also charted; hemodialysis intervals and per-session output chartings overlap on only 53% of their union): the `procedureevents` intervals whose label says dialysis, CRRT, CVVH or SCUF, minus "Dialysis Catheter" (an access line in for days) and "CRRT Filter Change" (zero length); the hourly CRRT settings in `chartevents` collapsed into intervals (a new one after a gap over `RRT_GAP_HOURS` = 3, each ending one hour after its last charting); and the per-session Hemodialysis Output as a one-minute marker. Overlapping pieces become one interval, so hours are never double counted; 00 O4 checked the collapse rule on the 2,271 stays with both sources (charting hours over interval hours: median 0.98, 76% of stays within 20%). Features: `rrt_at_tk`, `crrt_at_tk`, `rrt_24h`, `ihd_24h`, `rrt_hours_24h`; 01 table 11 prints the share of dialysis rows found only by charting. Antibiotics are the `inputevents` category "Antibiotics" (00 P: 617k one-minute administrations with no rate, antivirals and antifungals included, so "given in the last 24 h" is the feature and "running at t_k" would never fire): `antibiotic_24h`, `n_antibiotics_24h`, `antibiotic_started_24h` (the agent's first administration of the stay fell in the look-back) and `hrs_since_first_antibiotic`. Cultures are specimens in `hosp.microbiologyevents` collapsed to one row per `micro_specimen_id`, without the MRSA admission screen (00 P: 64,759 specimens, routine on admission, so it would fire on most first landmarks) and the serology and immunology panels: `n_cultures_24h`, `blood_culture_24h`. A specimen with only a collection date counts when that date is strictly before DATE(t_k) and not before DATE(t_k − 24 h), the omr rule; 00 P found 0.0% such specimens among the common types, so the rule is a guard that costs nothing in v3.1. `suspected_infection_24h` = a new antibiotic and a culture in the same look-back, a 24 h simplification of the Sepsis-3 suspicion window (72 h in the original) chosen so the flag cannot reach past t_k. `octreotide_24h` is an eMAR octreotide dose or infusion start (00 P2: 49,671 rows on 3,187 admissions) or an `inputevents` octreotide segment (7,295 rate rows on 1,785 stays), union of sources, the rule 00 L forced for insulin. No ICU severity score is computed: SOFA needs the same labs and vitals the model already sees, and the feature set says what it measured rather than borrowing a score's name.
- Lab panel values must be > 0 (except anion gap); the notebook winsorises every lab and glucose feature at the training-set 0.1 and 99.9 percentiles and applies the cut-points unchanged to the other splits.
- Features use the records the EHR held at t_k: lab and glucose values whose storetime (fallback charttime) AND charttime are both < t_k (the first ICU run found 948 landmark rows, 0.7%, whose latest value had been stored before t_k under a charttime at or after it; 02 Table 1b measures how often a nominal time trails the entry time: 11.35% of ICU glucose results in the release .22 run, a median 7 minutes, 941 landmark rows straddled), the same both-times rule for every other record (the Availability point below), ICU chart items in the last 24 h, omr chartdate < DATE(t_k), and diagnoses from admissions discharged before the current admittime only. `max_feature_time` is carried on every row for the assertion. The glucose features use every documented result known at t_k; nothing is removed on the feature side.
- Eras and the split: all five anchor_year_groups are built and `anchor_year_group` travels on every row. The `split` column comes from two DECLAREs in 01: `PRIMARY_TEST_ERA` = '2017 - 2019' (`test`) and `SHIFTED_TEST_ERA` = '2020 - 2022' (`test_shifted`), everything else `train`. The split is by the patient's anchor year group, so it is patient-disjoint and approximately temporal: a patient's anchor year lies in the group's range, but their later admissions keep the group whatever calendar year they fall in (table 17 shows admissions up to five years after the anchor), so "trained on 2008 to 2016" means "on patients anchored in 2008 to 2016". Every row carries `years_after_anchor` (admittime year minus anchor year, exact under MIMIC's date shift); table 19 tabulates it per split and the notebook's fourth sensitivity scores the anchor-year admissions alone. Patients anchored in 2017 to 2019 are the primary held-out group because the third ICU run's table 14 found inputevents rows on 37.7% and procedureevents rows on 40.6% of the 2020 to 2022 universe stays against 88 to 96% in every earlier era, with heart-rate and GCS charting complete in all of them: about 60% of the latest era's ICU stays have no flowsheet medication or procedure data, so drip rates, vasopressors, ventilation, feeds and antibiotics are missing for them. 2020 to 2022 is never trained on and is reported as the documentation-shift test; table 16 shows the gap by care unit (the fourth run: 31 to 40% of stays with inputevents in every ICU of 2020 to 2022 against 88 to 97% in 2017 to 2019, so not a unit's charting system) and table 17 by year relative to the anchor year (whether the export stopped on a date). Which training eras the models use is still a notebook setting read off tables 2, 10 and 14. To test on the latest era alone, set `PRIMARY_TEST_ERA` to '2020 - 2022' and `SHIFTED_TEST_ERA` to ''.
- Bookkeeping columns are never model inputs: ids, times, split, era, `years_after_anchor`, window_hours, race, insurance, language, marital status, the five labels, `label_window_n_glucose` (results in the label window: future information, reporting only) and the six drip-record flags.
- Availability, by kind of record (release .22; the second review of 12 October 2026 asked for it, and `tests/prefix_invariance.py` enforces it). The principle: a record enters a landmark's eligibility or predictors only if its entry time (storetime) and its own clinical time both precede t_k, and the same views serve the at-risk rule in `01` and the features in `02`. Point records (labs, glucose, vitals, weight, GCS, eMAR administrations and events, inputevents boluses) follow the both-times rule as written. Interval records (inputevents segments for insulin, feeds, dextrose, vasopressors, antibiotics and octreotide; procedureevents intervals) are visible from their storetime on, which table 20 (the same in the .20 and .22 runs) places at a median 1 minute after the segment's start and 67 minutes before its end for insulin drips (p90 83 minutes after the start, 13.9% more than an hour after): the row is entered when the infusion is started, and its end is written later with no entry time of its own. So a segment's start and rate are known from its entry; its end is known at t_k when the segment ended before t_k and, for a segment closed by a rate change, when the next segment was entered before t_k (`end_storetime` in `icu_insulin` and `icu_nutrition`, the one end whose entry time the data records); otherwise the segment is running at t_k and contributes only the part before t_k. An amount-derived rate (the rate-less "Continuous IV" rows, `amount / hours`) is the segment's total and is used only once the segment is complete at t_k. The eMAR infusion state is rebuilt at every landmark from the events charted and entered before it (`emar_drips_at_landmark`, the rules of view 2b over the visible events), so a Stopped entered after t_k cannot close an interval at t_k and a Stopped charted after the cap expired cannot reopen one; the flowsheet-source flag is true at t_k only when a segment had both started and been entered by then. Dialysis intervals are rebuilt the same way (`rrt_at_landmark`: the procedureevents intervals entered before t_k and the CRRT chartings entered before t_k, the end of a charting interval being its last visible charting plus one hour). That one-hour tail is conservative: the .22 run has dialysis at 4.36% of landmarks against 8.06% in .20, because a landmark that falls between an hourly charting and its entry (chartevents rows enter a median 22 minutes after their charttime, the vitals row of table 20) sees the interval as ended; the next release lengthens the tail to the island gap (`RRT_GAP_HOURS`). What the data cannot timestamp is stated rather than assumed: the end of a segment closed by a Stopped, Paused or FinishedRunning status is taken at its nominal time, and a culture is counted at its collection time because the microbiology row's storetime dates the result, days later (table 20 measures it), not the draw. Table 20 reports, per record kind, the entry lag; table 21 reports, per record kind, how many records in use at the landmarks by their clinical times had not been entered by then, which is what the rule withholds. The .22 run measured the price: 25.3% of the insulin drip segments running at a landmark had not been entered (2,608 landmark rows), 2.0% of segments in the look-back, 3.0% of flowsheet boluses, 0.5% of eMAR doses, 1.4% of eMAR infusion events, 4.1% of vasopressor and 2.7% of antibiotic segments, 7.9% of dialysis intervals, 1,940 rate changes written after the landmark (kept running at the earlier rate); and two records lose most of their rows: 57.9% of the feed and dextrose segments running at a landmark (table 20: feeds enter a median 28 minutes after their start, p90 12.5 hours) and 99.5% of the ventilation intervals, because procedureevents rows are written at the end of the procedure (table 20: a ventilation interval enters a median 26.8 hours after its start and 3 minutes after its end). The ventilation feature is therefore effectively withheld in release .22; the next release reads ventilation from the hourly ventilator settings in chartevents, which needs a new extract. The headline did not move between .20 and .22 (arm B 0.865 to 0.863 on the primary group, 0.855 to 0.852 on the shift group, inside the intervals), which says the ranking never leaned on the withheld records. The release .20 design had treated intervals as stored at their end and argued that a storetime rule would delete the running infusions; its own table 20 showed the opposite, and the rule above follows the measurement.
- The flowsheet-first flag is evaluated per landmark: `stay_has_inputevents_drip` is true when the flowsheet charted an insulin drip segment that started before t_k, so a segment charted later in the stay cannot change an earlier row (release .20; before it the flag was a stay-level fact).

## The models (stage 3 of notebooks/hypo_harm_tutorial.ipynb, src/hypo_tutorial/)

- Inputs are every column of `features` that is neither a label nor bookkeeping (`src/hypo_tutorial/columns.py` writes the roles out; a new SQL column is refused until it has one). `race`, `insurance`, `language` and `marital_status` are bookkeeping on purpose: a glucose-harm model has no business learning them, and they serve the subgroup tables. The six drip-record flags are bookkeeping because the eMAR-only drips sit mostly in 2020 to 2022 and would teach the model the era.
- Preparation is fitted on the training rows only (`features.py`), and inside the cross-validation it is refitted on each fold's training rows and applied to that fold's validation rows (`models.py`, release .20), so no validation-row statistic reaches the model scored on it; the preparation fitted on all training rows serves the final models and the test eras. It is: winsorising at the training 0.1 and 99.9 percentiles (00 H2 and H7: the raw tables carry heart rates of 10,000,000 and a 930-unit insulin day), a missing indicator for every input ever missing in training, training medians for the logistic arm, NaN kept for the tree arm, one-hot categories with levels under 50 training rows pooled into `other` and unseen test levels sent there too, standardisation for the logistic arm. The cut-points are written to `results/feature_prep_cutpoints.csv`.
- Arm A is an L2 logistic regression whose penalty is chosen on grouped cross-validated log loss over six values of C; arm B is LightGBM with fixed conservative settings (learning rate 0.03, 31 leaves, at least 100 rows per leaf, 80% feature and row subsampling, L2 of 1) and the number of trees set by early stopping on each fold's validation log loss, refit on all training rows with the mean best iteration (`models.py`). Folds are `StratifiedGroupKFold` by subject: a patient contributes up to 28 correlated rows, and a fold that splits them rewards memorising patients. Log loss is the criterion because the outputs are read as risks. Nothing is tuned on a test era. LightGBM runs with `deterministic=True` (and `force_row_wise`, which it asks for alongside) so two machines with different core counts reach the same trees, and the rows are sorted by subject, stay and landmark before the folds are drawn (a file pulled twice from BigQuery came back in a different order, which moved the folds and the third decimal of the AUROC between two runs on the same data); measured on 61k training rows by 207 columns on two cores, the five folds and the refit take about 21 s per outcome, and the setting costs no time.
- Out-of-fold predictions on the training rows feed a Platt recalibration (a logistic regression of the outcome on the model's logit) that is applied to the test eras next to the raw model; its fitted slope and intercept are printed, and a slope near 1 says the raw model was already calibrated.
- Evaluation (`evaluate.py`), per arm, outcome and era, with subject-level bootstrap intervals (1,000 draws; see the next point for how they are computed): AUROC and AUPRC; Brier score, O/E ratio, calibration slope and intercept, expected calibration error and a reliability table in risk deciles; decision curves over thresholds that follow the base rate (0.5 to 10% for < 54, 2 to 40% for > 300) against acting on every row and on none; operating points when the top 5, 10 and 20% of rows are flagged (sensitivity, PPV, alerts per 100 rows); subgroups by drip status, the record that saw the drip, era, care unit, sex, race (MIMIC's coarse groups) and ICU day, written to be shared as they are: levels under 100 rows are pooled, cells under 10 events (or non-events) carry no count and no metric; standardised coefficients for arm A and mean |SHAP| for arm B. `oof_calibration_*.csv` records how the out-of-fold predictions were calibrated and what the Platt step learned from them.
- The bootstrap draws subjects with replacement. Since release .9 a draw is computed as integer row weights (how many times each row's subject was drawn) over the rows sorted once by predicted risk: weighted AUROC in its Mann-Whitney form with ties counting one half, weighted average precision at the distinct predictions, weighted Brier and O/E, and the calibration slope and intercept by a two-parameter Newton-Raphson fit. This is the same arithmetic as stacking the drawn rows and calling scikit-learn, and `tests/test_evaluate.py` checks it: the weighted metrics equal scikit-learn's functions on the row-repeated table to 1e-10 (slope and intercept to 1e-7), and a 200-draw bootstrap gives the same intervals as the release .8 implementation to 1e-7. It is about twenty times faster (5 ms a draw against 100 ms on a test-era-sized problem), which turns the 16 bootstraps of the evaluation cell from half an hour into under two minutes on two cores. The point estimates in every table are still scikit-learn's own functions. The same test found that scikit-learn's default L-BFGS tolerance (1e-4) stops the slope and intercept fit early, with a gradient of order 1 left and the intercept off in the second to third decimal; `calibration_slope_intercept` and `Platt` now use tol=1e-8, so the slope, intercept and `+Platt` rows of a release .8 run differ from a .9 run in those decimals, while the raw arms' AUROC, AUPRC, Brier, O/E and ECE are identical.
- The two test groups are reported apart and never pooled: patients anchored in 2017 to 2019 are the primary test (approximately temporal, see the split above); those anchored in 2020 to 2022 are the documentation-shift test, where about 60% of stays have no flowsheet medication or procedure data (tables 14, 16 and 17), so its numbers measure the model under a charting change, not the patients.
- Sensitivities on arm B for < 54: training on 2011 to 2016 only (the first era's low-glucose rate stands apart), scoring the measured rows only (`label_window_n_glucose > 0`), scoring the windows of 6 h or more, scoring the anchor-year admissions alone, and (release .22) refitting arm B on the repeat-excluded endpoint `y_lt54_excl_24h` and scoring it against that endpoint.
- Reporting follows TRIPOD+AI (Collins et al., BMJ 2024;385:e078378): discrimination, calibration and clinical utility, with the sample-size reasoning of Riley et al. (Statistics in Medicine 2019;38:1276) in `docs/cohort_findings.md`, the calibration hierarchy of Van Calster et al. (BMC Medicine 2019;17:230) and decision curves after Vickers and Elkin (Medical Decision Making 2006;26:565).


## Cost (BigQuery on-demand), and why a student fits in the free tier

BigQuery bills a query by the bytes of the columns it reads, not by the rows it returns. The `physionet-data` tables are neither partitioned nor clustered, so any query that names `icu.chartevents` (433 million rows) reads the whole of each column it uses, 3.2 GiB per 8-byte column, whatever its WHERE clause; `hosp.labevents` (158 million rows) and `hosp.emar_detail` cost a few GiB a scan each. Two limits apply to a project without a billing account, which is what a student has (a "sandbox"): 1 TiB of query bytes per month, which refills, and a lifetime 10 GiB of storage, which does not: Google's sandbox page grants "a lifetime limit of 10 GiB of storage" and says "this quota is not refunded upon data deletion" ([docs](https://docs.cloud.google.com/bigquery/docs/sandbox)). Every `CREATE OR REPLACE TABLE` spends it, dropping a table returns nothing, tables expire after 60 days, and DML is not supported. The author's project of the first attempts spent its 10 GiB on 10 October 2026 and can never store again; that is the failure this design is built around.

The design, in three rules. First, one pass. `00b_extract.sql` reads each large table once and writes only the rows and columns later files read, then `01` and `02` are views over those extracts plus two one-row tables and `cohort_landmarks`, so a re-run after a DECLARE change costs query bytes, which refill, and no storage, which does not. Second, the universe. The cohort is "ICU days with a hypoglycemic agent in the previous 24 h", so `00b` first finds the admissions in which insulin, a sulfonylurea or a meglitinide appears before the last ICU discharge (either source, any event text: a superset of what `01` counts as a dose) and keeps only their labs, eMAR, flowsheet and procedure rows; ICU glucose is kept for every stay because tables 9 and 10 of `01` report meter zeros and hypoglycemia across all eligible stays. The agent patterns are written to `hypo_tutorial.agent_patterns` by `00b` and read from there by `01`, so the universe and the classification share one definition; changing the agents is a new extract, by construction. Third, items first. Every extract is clustered by `itemid`, so the glucose, dialysis and vasopressor queries read only their blocks; the vitals are most of `src_chartevents` and are read whole by `02`, the one scan that cannot be cheaper. From `inputevents` only the items the pipeline names are kept: insulin and octreotide by label, the seven mimic-code vasopressors by id, every antibiotic and nutrition item, and the dextrose fluids; the other 4 million "Medications" rows are never read.

What the free tier buys a student. Every row is measured (11 October 2026, a billing-enabled project, MIMIC-IV v3.1: the extract 29.1 GiB billed in 39 seconds, 2.47 GiB written, before release .20 added the entry-time columns, which read about 3 GiB more and store 2.78 GiB; `01` 6.0 GiB in 100 seconds over 31 statements, 34 since release .20 and 39 since .22, which also writes `landmark_grid`, a table of a few hundred thousand short rows, and `02` 5.4 GiB in 40 seconds over 4; the pull 2.98 GiB in 37 seconds; the .22 rerun's numbers replace these). A re-run bills less for the tables that read only the extracts and physionet-data (tables 10, 12, 14, 16, 17): BigQuery serves an identical query over unchanged tables from its result cache at no cost, which is why the sixth run's `01` billed 4.6 GiB:

So a student who runs the extract once, the pipeline twenty times (about 12 GiB a run) and the pull a few times (3 GiB each) stays near 250 GiB of the monthly TiB, and nothing they are asked to run writes more than the extract's 2.78 GiB. The universe is 44,163 of the 85,229 admissions with an ICU stay (52%), which is what cut the extract from the 4.5 GB of the first design to 2.47 GiB (2.78 with the entry-time columns). `pipeline/run_bigquery.py --step cost` prints both counters at any time. The rules this implies: run `00b` exactly once per project and never `CREATE OR REPLACE` its tables again; never re-run `00` for routine work; check the console's estimate before any statement that names `physionet-data`; do the pull soon after the pipeline, because sandbox tables expire after 60 days; if a storage quota error appears, do not delete and retry, start a new project (the runner's probe catches this in seconds); if a "custom quota exceeded" error names QueryUsagePerDay, someone set a daily cost control on the project (the default is 200 TiB a day; enabling billing can prompt for one), and the fix is IAM & Admin, Quotas & System Limits, BigQuery API, Query usage per day, Edit, a value in TiB or Unlimited, or waiting for the reset at midnight US Pacific. The runner saves the check tables of every statement that completed before a failure, so nothing already paid for is lost. A project with billing has none of these constraints and pays about $0.02 per GB-month for the extracts and $6.25 per TiB of query bytes past the free tier.

Measured on 11 October 2026 (`INFORMATION_SCHEMA.JOBS_BY_USER`, before the extract existed): the old design cost 0.325 TiB over 237 statements for the month (five sanity runs, three hospital-wide cohort runs, one partial ICU run). Per statement of the old design: `glucose_events` 19.3 GiB, `features` 18.6, `serialized` 18.7, `icu_rrt` 12.9 (two chartevents scans), 01 table 9 11.0, 01 table 10 9.7, 00 sections O3 and O4 9.7 each, 00 A/B 8.8, O 6.8, H6 6.7, O2 6.5, `emar_cohort` 5.6, H2 and C 5.1; everything on `inputevents` about 1 GiB or less. A pass of 01 to 03 was therefore about 100 GiB and a sanity run 60 to 80. The month's spend, with the parent script rows excluded so nothing counts twice:

```sql
SELECT DATE(creation_time) AS day,
       LEFT(REGEXP_REPLACE(query, r'\s+', ' '), 90) AS query_start,
       statement_type,
       ROUND(total_bytes_billed / POW(1024, 3), 1) AS gib_billed
FROM `YOUR_PROJECT.region-us.INFORMATION_SCHEMA.JOBS_BY_USER`
WHERE creation_time >= TIMESTAMP_TRUNC(CURRENT_TIMESTAMP(), MONTH)
  AND job_type = 'QUERY'
  AND COALESCE(statement_type, '') != 'SCRIPT'
ORDER BY gib_billed DESC;
```
